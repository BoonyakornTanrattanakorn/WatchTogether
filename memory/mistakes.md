# Mistakes

Bugs that cost real time to find, written down so they are not rediscovered.
Each one records the symptom as it was actually reported, the mechanism, and —
most usefully — **what would have found it sooner**.

Companion to [architecture.md](architecture.md).

The recurring theme, stated once up front: **the reported symptom named the
wrong subsystem almost every time.** "Can't log in on a VPN" was an encoding
bug. "Client can't see subtitles" was three unrelated causes across two
sessions. "Video won't play" is usually a missing codec reported as a network
error. Treat the reported symptom as a starting location, never as a diagnosis.

---

## 1. `body += chunk` corrupted every non-ASCII password

**Reported as:** "somehow i can't login if i use vpn", with two failed-login log
lines from different IPs.

**Actually:** `readBody()` accumulated the POST body with `body += chunk`, which
coerces each `Buffer` to a UTF-8 string *independently*. A multi-byte character
split across a TCP chunk boundary decodes as two invalid halves and becomes
replacement characters. The password no longer matches.

A VPN changes MTU and timing, and therefore changes where chunks split. That is
the entire connection to the VPN. It corrupted usernames and invite codes the
same way.

**Measured:** for a body containing 2-, 3- and 4-byte UTF-8 characters, **11 of
52 possible split points** corrupted it. Roughly a one-in-five failure rate,
which is exactly the "works sometimes" profile that makes a bug look
environmental.

**Fix:** collect chunks as Buffers, `Buffer.concat(chunks).toString('utf8')`
once at the end. The size cap counts bytes, not string length.

**What would have found it sooner:** noticing that the log line
`! failed login for "<name>"` only fires on a *wrong password*, never on rate
limiting — which immediately rules out the IP-based explanation the symptom
suggests. The rate limiter returns 429 before reaching that line.

**Trap in the test:** the first regression test passed against the *broken*
code. `encodeURIComponent` percent-encodes non-ASCII, so a browser form submit
is pure ASCII on the wire and can never trigger this. The test has to send raw
UTF-8, which is what non-percent-encoding clients send — and is exactly the
population the bug hurt. **Always verify a regression test fails against the
unfixed code.** `test/body.js` does this; it was confirmed to fail 4/4 when
`readBody` was temporarily reverted.

## 2. The echo guard swallowed everything, not just echoes

**Reported as:** "if i seek while the video is playing the client will just see
the video paused while admin sees the video playing normally".

**Actually:** the client had one `send()` that suppressed **all** outbound
WebSocket messages for 300ms after applying a state message. The guard exists
for one thing — a `control` generated by our own seek/play/pause while obeying
the room, which would bounce the room's state back at it.

But it was also swallowing `stall` and `ready`. A seek fires the `waiting` event
inside exactly that 300ms window, so the viewer's `stall` never reached the
server. The room never learned they were buffering, the matching `ready` could
be dropped too, and the viewer sat on a still frame while the host played on.

The host heartbeat (every 2s) made that window of silence come round constantly.

**It was also silently dropping admin commands** — clicking Encode just after a
state message did nothing at all. Found while fixing the above; never reported,
because a button that does nothing gets clicked again.

**Fix:** the guard applies only to `control`, named in an `ECHOABLE` set.
Additionally `ready` re-issues `play()` when the room is playing and we are
paused, so a seek cannot strand a viewer.

**What would have found it sooner:** asking what the guard is actually *for*.
Only messages the server can replay at us can echo. A buffer report and a
deliberate admin instruction are neither. A blanket gate over a whole transport
is almost always too broad.

## 3. Subtitles: three different causes, two sessions

The same reported symptom — "the client still doesn't see subtitle" — had three
unrelated causes. Fixing one made the next visible.

### 3a. Wrong stream index

`/subs/<id>/<n>` mapped `-map 0:s:<n>`, where `n` indexed the *published* list.
That list has bitmap formats (PGS, VOBSUB) filtered out, but `0:s:<n>` counts
every subtitle stream in the file — so a file whose first subtitle stream is PGS
hands back the PGS track under the ASS track's number, and the request yields
nothing usable.

It happened to work on the test library, whose ASS tracks come first. Reorder
the streams and it breaks silently.

**Fix:** map by the stream's absolute index, which the probe already recorded.
An out-of-range track is now a 404 rather than an empty 200 that hangs.

### 3b. The renderer was never rebuilt

`apply()` only called `applyTracks()` when the room's track numbers *changed*.
A renderer torn down by a reconnect or a source swap was never rebuilt, because
the room's choice still matched ours and nothing asked for it again.

**Fix:** re-assert on every state message; `startJassub` is idempotent.

### 3c. …which then destroyed the renderer on every heartbeat

The fix for 3b caused a new bug. `applyTracks()` falls through to the WebVTT
branch whenever the track list is not loaded yet — and that branch *begins* by
calling `destroyJassub()`. So a routine heartbeat arriving while the `/tracks/`
probe was still in flight tore down a working libass canvas, and nothing
rebuilt it.

The obvious guard does not work: `tracksFor` is claimed *before* the fetch
starts, so it already names the new file and cannot distinguish "not loaded yet"
from "loaded, and it's this one".

**Fix:** a second flag, `tracksReadyFor`, records which file the list actually
*describes*. `applyTracks` returns early unless it matches. Re-assertion stays;
only the teardown-on-unknown-list is gone.

**What would have found it sooner:** when a fix makes something re-run far more
often, check every path it can now take — especially destructive ones. The
teardown was always there; it only became harmful once the function ran every
two seconds instead of on a track change.

## 4. Sync: four compounding bugs under one complaint

**Reported as:** "the sync is horrible now. the client could somehow be ahead of
admin and it's not trying to sync."

Four separate defects, each individually plausible:

1. **A dead band.** The drift loop hard-seeked above 2s, but on the transcode
   path `seekInFile` refused to restart an encode for anything under 3s. A
   viewer between 2s and 3s out took the seek branch, was refused, and never
   reached the rate-nudge branch either. They stayed wrong **indefinitely** —
   precisely "not even trying". The two thresholds were defined far apart in the
   file and drifted apart during editing.

2. **The host corrected against itself.** `isHost` was never checked, so the
   host ran the follower correction against room time — which *is* the host's
   own last report. Circular, and it meant the correction fought the person it
   was following, nudging their rate and eventually seeking them mid-scene.

3. **The anchor went stale.** `room.time`/`updatedAt` only moved when the host
   pressed something. An hour into an untouched film, everyone was extrapolating
   from an hour-old reading, and the host's own playback rate is never exactly
   1.0 — so the reference itself had drifted from what viewers were held to,
   with nothing able to correct it.

4. **The clock offset was one noisy sample.** `offset` was replaced by the
   newest ping/pong every 15s, so a single round trip that queued behind a video
   segment moved every sync decision by however long that took.

**Fixes:** thresholds defined adjacent to each other with no gap; drift
correction runs on viewers only; the host heartbeats its true position every 2s
and the server re-anchors (broadcasting only when it moved >0.5s); the clock
keeps 8 samples and takes the **lowest-RTT** one.

**What would have found it sooner:** writing out the correction as a table of
drift → action and checking every value is covered. The dead band is obvious the
moment you do that, and invisible when the two thresholds live 500 lines apart.
There is now a check that no drift value falls between the bands.

## 5. Capping the video instead of the stage

**Found while verifying**, not reported. Inside `@media (max-width: 60rem)` the
rule was `body.host video { max-height: 45dvh }` — capping the video but **not**
the `#stage` box around it.

At 800×600 as an admin: stage 436.5px tall, video 270px inside it. Since the
subtitle canvas is positioned against the stage, subtitles were drawn ~166px
**below** the picture.

**Fix:** `body.host #stage { max-height: 45dvh }`, so the two shrink together.

**The invariant to remember:** the stage must always be exactly the rendered
picture. Anything that resizes the video must resize the stage instead. Both
the subtitle canvas and the autoplay overlay depend on this.

**What found it:** driving headless Edge over CDP and comparing
`#stage.getBoundingClientRect()` against `#v`'s at eight viewport sizes × two
roles. Seven of eight matched; the eighth did not. This kind of thing is not
visible by reading CSS and is trivial to measure.

## 5b. `aspect-ratio` silently ignored, so the stage was never the picture

**Reported as:** "there's an aspect ration problem with the current full screen
button. why not just use media player full screen? it already worked perfectly",
then — after a first attempt that made it worse — "now there's not subtitle????"
and "the aspect ratio problem is still here. note that i'm trying to watch 4:3
video which is different from usual 16:9 screen".

The second report is the one that cracked it. **The file ratio was the variable
that mattered, and it took being told twice.** Everything had been tested with
16:9 fixtures, where box and picture coincide and every one of these bugs is
invisible.

**Actually:** nothing to do with fullscreen — fullscreen was the one geometry
that was *right*. `#stage` carried `width: 100%; height: 100%` alongside
`aspect-ratio: var(--ar)`. **`aspect-ratio` is ignored when both axes are
definite**, so the ratio had never done anything: the stage stretched to fill
the pane and the picture letterboxed itself *inside* a stage of the wrong
shape.

So mistake 5's invariant — the stage is exactly the rendered picture — was
being violated everywhere, not just in the one capped case 5 fixed. Measured at
1920×1080 as a guest: stage 1100×996 around a picture of 1100×619, putting
subtitles ~190px below the frame. **0/15** viewport × file-ratio combinations
had stage === picture.

**Fix:** `width: min(1100px, 100%)` with `max-height: 100%` and no `height`.
**Exactly one** axis definite — not zero, not two.

Zero is its own bug, and I shipped it for one round before catching it: with
maxima only, `main`'s `place-items: center` makes the stage shrink-to-fit, so
it collapses to the *video's intrinsic size*. A 640x480 file then played at
640x480 in the middle of a 1920x1080 window. A 1080p file looks roughly right
that way, which is exactly why the first round of testing missed it — the
fixture has to be the awkward ratio, not the common one.

**What would have found it sooner:** the giveaway was in the measurements
already — the numbers were *identical* with `--ar` set and with it absent. A
variable that changes nothing when it changes is not being read. Measuring the
control case alongside the real one costs nothing and makes "this rule is inert"
obvious, where measuring only the real case just looks like a wrong number.

**The general rule:** `aspect-ratio` needs exactly one free axis. Both definite
and it is ignored; neither definite and a centring parent collapses the box to
its content.

### 5c. `place-items: center` cut the bottom off a 4:3 picture in fullscreen

Part of the same report, found only by screenshotting the real thing. The
fullscreen rule used `display: grid; place-items: center` on the stage. Centring
makes the video shrink-to-fit its own content rather than honouring
`height: 100%`, so a 4:3 file rendered **1920x1440 inside a 1080-tall screen** —
360px of overflow, taking the bottom of the picture with it. Subtitles live at
the bottom of the picture, so they were the part that got cut.

`display: block` with the video at `100%/100%` and `object-fit: contain`
letterboxes correctly at every ratio.

**Note for next time:** the stage genuinely *is* the screen in fullscreen, not
the picture — the UA stylesheet forces `width/height: 100%` with
`max-width/max-height: none` at a precedence an id selector cannot beat. Trying
to make the stage the picture there is wasted effort; I wrote a rule to do it
and measured it having no effect at all. It does not matter, because jassub
positions the canvas from the *video's* box and sets the canvas's own
width/height/top/left — so subtitles track the picture regardless of what the
offset parent is doing.

**What found it:** a screenshot. The numbers had said "canvas === picture, 0.0px
off" while the picture itself was hanging off the bottom of the screen — the
measurement was self-consistent and still described a broken page. Rendering the
thing and looking at it is the check that cannot be fooled this way.

## 7. A silently swallowed `.catch()` looked like "fullscreen doesn't work"

**Reported as:** "why is full screen from media player not allowed? is it not
possible at all?", then "you have to prompt the user since right now they just
see that media player don't let them fullscreen".

**Actually:** the native `<video>` fullscreen button *does* trigger fullscreen
— briefly. The page's own `fullscreenchange` handler detects it, calls
`exitFullscreen()`, and tries to promote `#stage` instead (subtitles have to
ride along, and they can't attach to a fullscreen `<video>`; see the comment
above this entry). That promotion request happened inside a `.then()`, not
inside the original click — and browsers only grant `requestFullscreen()`
inside the call stack of a real user gesture. Confirmed by direct test:
`stageEl.requestFullscreen()` there throws `Permissions check failed`. So the
promotion failed every time, silently, behind a bare `.catch(() => {})` — the
viewer saw fullscreen engage for an instant and then drop back to the normal
page, with nothing to tell them why or what to do instead.

Also tried: swapping the fullscreen element directly without an intervening
`exitFullscreen()` (some engines allow replacing the fullscreen element from a
handler without a fresh gesture). Also refused, same error. **There is no
programmatic way to make this promotion reliable** — the fix is a `notice()`
in the `.catch()` pointing at the app's own fullscreen button, not a cleverer
retry.

**What would have found it sooner:** a bare `catch(() => {})` on anything
user-initiated should be treated as a missing error path until proven
otherwise, not a safe default. It was written that way from the start and
never revisited because nothing *threw* during the sessions that built it —
Chrome only refuses this on gestures that have already been spent, which a
synthetic click-and-check misses unless it drives the *actual* native control,
not a stand-in for it.

## 6. A test that silently stopped testing

`test/cpu.js` built its fixture by encoding 600s of 1080p HEVC within a 120s
budget. Marginal enough that on a loaded machine it missed — and the failure
mode was the suite printing `note: no ffmpeg/libx265, skipping` and exiting **0**
with every assertion unrun.

It had been passing minutes earlier, which is the only reason it was noticed.

**Fix:** the fixture is 4fps instead of 24 (the re-encode still walks the whole
timeline, so it stays slow enough to observe mid-flight) with a larger budget,
and a fixture *timeout* now exits 1 rather than masquerading as a legitimate
skip. ~2 minutes and flaky → ~40s reliable, all 12 assertions running.

**The general rule:** a skip path that is indistinguishable from a pass will
eventually be taken. Distinguish "this machine cannot run this test" from "this
test failed to set itself up" and fail the second.

**Related:** `npm test` chains suites with `&&`, so a suite that prints
`all passed` and *then* crashes (as `cpu.js` once did, on a missing directory)
can be missed entirely if you only read the summary lines. Check the exit code.

## Habits that paid off

- **Reproduce the mechanism in isolation before fixing.** The 11-of-52 split
  measurement took two minutes and turned "maybe a VPN thing" into a certainty.
- **Verify a regression test fails against the unfixed code.** Caught one test
  that was passing for the wrong reason.
- **Measure layout in a real browser.** CDP + `getBoundingClientRect` found a
  bug that reading CSS would not have.
- **Check what is still *running* after a test, not just what it returned.**
  That is the entire reason `cpu.js` exists.
- **When a symptom names a subsystem, check the plumbing first.** Login → body
  parsing. Subtitles → stream indexing. Sync → the clock.
